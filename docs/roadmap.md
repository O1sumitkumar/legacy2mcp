# Roadmap

## v0.1

- SOAP/WSDL adapter: introspects any WSDL via `zeep`, generates one MCP
  tool per operation with a real JSON Schema built from the WSDL's XSD
  types, validates every call against that schema before invoking the
  SOAP endpoint, and audit-logs every call (start/success/error) to a
  local JSONL file.
- Safety defaults: operations whose names look like writes
  (`Create*`, `Update*`, `Delete*`, `Cancel*`, `Submit*`, ...) are
  excluded unless `allow_write_operations: true` is set explicitly on
  that adapter. `include_operations` / `exclude_operations` allowlists
  on top of that.
- `stdio` transport only (the transport Claude Desktop and most MCP
  clients spawn servers over).
- Basic auth support for the WSDL endpoint (`auth.type: basic`).
- CLI: `legacy2mcp run --config ...` and `legacy2mcp inspect --config ...`
  (dry-run tool discovery, no server started -- useful in CI to catch
  a broken WSDL before deploying).

## v0.2

- **Database adapter** (`type: db`) -- ✅ shipped: introspects a live
  Postgres / SQL Server / Oracle schema and exposes `select_<table>` /
  `insert_<table>` tools for an explicit allowlist of tables and
  operations, plus named parameterized queries defined in config. No
  arbitrary SQL from the LLM, ever -- the LLM only ever supplies
  placeholder values for a query someone wrote into config, never SQL
  text. `insert_<table>` and write-marked named queries additionally
  require `allow_write_operations: true`. Postgres is the
  best-exercised dialect; SQL Server (`pyodbc`) and Oracle
  (`oracledb`) share the same adapter and safety model but have less
  real-world mileage -- see `docs/security.md`.
- **HTTP/SSE transport**, for MCP clients that talk HTTP instead of
  spawning a stdio subprocess. (planned, not implemented)
- Fine-grained authorization: map an identity's role or attributes to
  an allowed tool-name pattern (`select_*`, `get_*`, etc.). (planned)
- OAuth2 auth for SOAP endpoints (basic auth only today). (planned)

## v0.2.x -- REST adapter + `legacy2mcp init`

- **REST adapter** (`type: rest`) -- ✅ shipped: unlike SOAP/DB there's no
  WSDL or live schema to introspect a plain HTTP API from, so the endpoint
  list (method, path, typed params) is explicit config -- hand-written, or
  generated by `legacy2mcp init`. Auth: none, basic, or bearer
  (`token_env`). Endpoints default to read-only; non-`GET` endpoints need
  `allow_write_operations: true`, same posture as every other adapter.
- **`legacy2mcp init`** -- ✅ shipped: asks (interactively, or via a flag)
  what to point legacy2mcp at -- a WSDL URL (points a `soap` adapter at it
  directly, no scan needed), a REST API URL (tries OpenAPI/Swagger
  discovery against it), or a GitHub repo/local path, which it statically
  scans (AST only, no execution) for a `zeep.Client(...)` call, a
  SQLAlchemy/Flask-SQLAlchemy model, or Flask/FastAPI route decorators --
  and writes a starter `config.yaml` for the matching adapter type. Only
  the GitHub/source-code path can use an LLM, and only to refine what
  static analysis already found: an OpenAI-compatible API key
  (`--llm-api-key-env` or an interactive, hidden prompt -- never written to
  disk) lets it refine ambiguous parameter types and read/write
  classification; without one, or with `--scan-only`, it
  runs static-only. See `src/legacy2mcp/discovery/` and
  [docs/security.md](security.md) for what this heuristic does and doesn't
  guarantee.

## v0.2.x -- Discover mode

- **`legacy2mcp discover`** -- ✅ shipped: an explicit upstream step before
  `init`, for sources it can't read directly -- a Postman Collection
  (`--postman-file`), a local OpenAPI/Swagger spec file (`--openapi-file`),
  a database's live stored-procedure/function catalog (`--stored-procs`),
  a HAR traffic capture (`--har-file` -- from browser devtools, Postman's
  own capture, or mitmproxy's built-in `mitmdump --set hardump=out.har`
  exporter; legacy2mcp never drives a capture proxy itself), a small
  hand-written queue description (`--queue-config`), or a plain webpage
  with no API docs at all (`--webpage-url` -- fetches the page and turns
  every `<form>` in its static HTML into a REST operation; no JavaScript
  executed, nothing ever submitted). Writes a Legacy
  Interface Contract (`contract.yaml`): every operation's inputs, outputs,
  enums, error codes, read/write side effect, and a confidence level (how
  the finding was made -- a live catalog vs. a curated artifact vs.
  inferred from sampled traffic), for a human to review before anything
  becomes runnable.
- **`legacy2mcp init --from-contract`** -- ✅ shipped: turns a reviewed
  contract into the same `config.yaml` the other `init` paths produce.
  Only REST-shaped operations are runnable today -- stored-procedure and
  queue findings are still captured in the contract for documentation, but
  get skipped with an explanatory TODO rather than silently dropped, since
  no adapter can call them yet (see Queue adapter and stored-procedure
  support below).
- **`describe_capabilities`** -- ✅ shipped: every generated MCP server now
  exposes one extra, always-on, read-only meta-tool so a connected agent
  can ask "what can this system do?" (every other tool's description,
  side effect, confidence, required fields, known error codes) before
  calling anything for real.

## v0.3+ (ideas, unscheduled)

- **Queue adapter** (`type: queue`): publish/subscribe tools for
  Kafka, RabbitMQ, SQS. `legacy2mcp discover --queue-config` already
  captures queue descriptions into a contract today; this is the
  still-missing runtime half that would let `init --from-contract` turn
  one into an actual tool.
- **Stored-procedure calling** (`type: db`, extended): `legacy2mcp
  discover --stored-procs` already reads a live procedure/function catalog
  into a contract; calling one at runtime -- with the same named,
  parameterized-only posture the `db` adapter already uses for tables and
  queries -- is still future work.
- Multi-step workflow composition with human-in-the-loop approval
  gates (chain several tools into one guarded operation).
- OpenTelemetry tracing export (spans per tool call) alongside the
  existing file-based audit log.
- Community-contributed adapters for other legacy protocols (mainframe
  RPC, SAP RFC, etc.).

Contributions on any of the above are welcome -- see CONTRIBUTING.md
(coming soon) or open an issue describing the adapter you want to add.
The `BaseAdapter` interface in `src/legacy2mcp/adapters/base.py` is the
extension point: implement `discover_tools()` and `invoke()`, and the
MCP server core in `server.py` handles the rest (validation, dispatch,
audit logging) without any changes.
